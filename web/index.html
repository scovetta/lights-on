The work that keeps coming back

Maintenance, not reinvention.

Lights On is built for stable projects that still need care. You define what belongs in the project; the automation works within that purpose.

01 / ISSUES

Keep the conversation moving

Classify reports, answer usage questions, ask for reproductions and propose fixes using repository context and the threat model.

02 / DEPENDENCIES

Handle the next update

Scan advisories and maintenance health. Prepare eligible npm patch/minor updates, or plan migrations that need your approval before execution.

03 / SECURITY

Work through security findings

Assess OSV findings against the project's security contract and propose fixes. Verification depends on the tools and offline cache you provide.

04 / DOCUMENTATION

Make the answers easier to find

Turn usage questions and repository context into documentation changes, and address instructions that have drifted from the code.

05 / PULL REQUESTS

Review before anything merges

Review intended use, compatibility and tests. Controller checks enforce the configured author, file, review and current-CI requirements.

06 / RELEASES

Prepare the next patch or minor

Propose release PRs, then build and publish through separate jobs. Releases have their own controls and registry setup; enable them deliberately.

Scanning is not the same as update support.

Scans cover several ecosystems. Routine updates currently need an eligible npm package-lock.json v2/v3 project, an existing test script and an offline cache. Workspaces and competing lockfiles block that path. Read the maintenance guide →

How it works

The model proposes.
Your policy decides.

GitHub Actions is the primary home for Lights On. Trusted controller code calls a provider, dispatches tools and checks the result before publication.

Model-requested commands run in a restricted Docker worker without network access or credentials. The publisher writes to the installed repository; upstream repositories remain read-only.

Read the architecture and boundaries →
/

A separate place to work

Candidate file tools operate on a temporary copy. Commands stay in the offline worker, not the controller's host shell.

?

Evidence before a merge

Independent review and explicitly configured CI checks are required by default. An empty required-check list blocks ordinary auto-merge.

!

Still needs an owner

Tests and model reviews can miss defects. Keep source checkouts free of secrets: source and task context may be sent to the selected provider.

Start small. Read the results.

Give it a project, not a blank check.

Use a repository you maintain or your own maintenance fork on GitHub.com. Start with merges and releases disabled while you check the work.

  1. 01

    Review and install the files

    Check that the target's origin points to the repository you intend to maintain. Run the installer from a reviewed Lights On source checkout; replace the example paths.

    The target directory must exist. Preview first, then remove the dry-run flag to install. The installer does not commit or push.

    Shell Linux / macOS
    sh /path/to/lights-on/install.sh /path/to/my-project --dry-run
    PowerShell Windows
    & C:\src\lights-on\install.ps1 -TargetDir C:\src\my-project -DryRun

    Existing .github/lights-on.yml is preserved unless forced; bundled automation files are replaced. Installation side effects

  2. 02

    Choose a provider and limits

    Add one provider secret in Settings > Secrets and variables > Actions. Confirm your account has access to the selected model.

    Under Settings > Actions > General, allow the installed workflows to write repository content and create pull requests. Organization policy may restrict this.

    Before paying for unattended work

    Leave events.allow_external_triggers: false. External issue, comment and PR activity then needs maintainer authorization before paid inference; scheduled and manual work still runs.

    The default is 25 tool-loop turns per provider attempt, with additional token and model-call limits. Use provider-side spending caps too: recorded quotas are not a hard global bill, and Copilot dollar cost is unknown.

    Limits and accounting →
  3. 03

    Start in review-only mode

    Edit the existing keys in .github/lights-on.yml; do not append duplicate sections. These are recommended rollout settings, not all shipped defaults.

    Review-only still allows comments, branches and PRs. It prevents automatic merging, but does not disable releases. Set the separate release switch to false.

    .github/lights-on.yml Initial rollout
    autonomy:
  mode: review-only
  require_ci_pass: true
  require_independent_agent_review: true
  required_checks: []

release:
  enabled: false

toolchains:
  enabled: false
  4. 04

    Prepare the worker, then run

    The supplied Actions workflows use Ubuntu runners and Docker. The default worker provides Node.js; supply other tools and the offline dependencies your tests need.

    Review and commit the installed .github files, then push. Open Actions > Lights On - Scheduled Maintenance > Run workflow and select bootstrap.

    Inspect a complete proposal and review cycle

    Read the run summary and any threat-model PR. Confirm your normal CI and the independent review jobs actually ran: GitHub can suppress follow-on events caused by GITHUB_TOKEN. Use manual dispatches when needed.

    Before enabling merges, set exact required check names and App IDs, match the PR gate's CI workflow names, and configure branch protection. The empty check list above deliberately blocks ordinary auto-merge.

Decisions that stay with you

Choose what can happen next.

Proposing a change, merging it and publishing a package are different permissions. Configure each before leaving work unattended.

Make CI requirements explicit

Use individual check names and their publishing App IDs, not just workflow names. Discovery can propose a list from enforced GitHub rules; review it before writing configuration.

Discover required checks →

Authorize wider changes separately

External PR auto-merge is off by default. Dependency migrations need an approved plan and a manual execution task. Optional Node toolchain proposals carry a review hold.

Task-specific controls →

Keep releases off until ready

Set release.enabled: false during rollout. Before enabling it, check package identity, registry authentication and the separate build/upload path.

Release setup →

Know how to stop new jobs

Set the repository variable LIGHTS_ON_ENABLED to the literal false to stop new Lights On jobs. Inspect any in-flight runs and already-published changes separately.

Optional / Linux and WSL

Need a protected local run?

The local launcher uses an operator-owned policy, audited default-deny network access and offline workers. It does not execute Actions YAML, and publication needs explicit grants. Unsupported tests remain blockers.
